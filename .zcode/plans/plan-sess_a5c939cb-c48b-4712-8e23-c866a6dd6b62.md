## Goal
Prepare the project structure so a future Flask GUI (config passed in-memory, never via `.env`) can reuse all business logic with zero rework. **No Flask code is written now** — only a clean refactor of the core.

## Key principle
All business logic becomes a reusable service that takes config as **constructor parameters**. The CLI keeps reading `.env` (via `ConfigLoader`) and feeds it into the service. A future Flask app passes form input directly as the same params.

## Changes

### 1. New file: `core/service.py` — `TaggerService`
The reusable orchestration layer (currently tangled inside `main.py`). Owns the full pipeline: scan → AI analyze → clear metadata → write metadata → rename → log → report progress.

- **Constructor**: `TaggerService(api_key, api_url, model, request_delay_seconds, music_directory, logger=None)`
  - Builds its own `GroqClient`, `FileScanner`, `FileProcessor` internally.
  - `logger` is optional (CLI passes one; future Flask can pass one or omit).
- **`scan()`** → returns `(audio_files, count)`. Reuses `FileScanner`.
- **`process_all(on_progress=None)`** → the main loop as a generator/callback:
  - Iterates files, calls `FileProcessor.process_file`, renames via `FileRenamer`, logs via `Logger`.
  - Calls `on_progress(index, total, result, new_filename)` after each file (CLI uses it to print; Flask will use it to update a view/SSE).
  - Returns a summary dict `{total, successful, failed, success_rate}`.
  - Progress callback is optional, so the service works with or without a UI attached.
- No imports of `cli/` — stays GUI-agnostic. This is the single reusable entry point both frontends will call.

### 2. Edit `core/__init__.py`
Export `TaggerService` alongside the existing classes.

### 3. Edit `main.py` — thin CLI wrapper
Replace the inline processing loop with:
- Read `.env` via `ConfigLoader` (unchanged).
- Instantiate `TaggerService` with the config values.
- Define a small `_cli_progress(...)` callback that calls the existing `cli.print_processing_start` / `print_processing_result` methods.
- Call `service.process_all(on_progress=_cli_progress)` and print the summary.
- Net effect: **identical CLI behavior**, but `main.py` shrinks to ~30 lines and contains no business logic.

### 4. Edit `README.md` + `ARCHITECTURE.md` (doc accuracy)
- Document the new `core/service.py` module and the `TaggerService` as the shared entry point.
- Add a short note: "A future Flask GUI can instantiate `TaggerService` directly with form-provided config — it does not require `.env`."

## What does NOT change
- `ai/`, `metadata/`, `utils/`, `cli/`, `logs/` modules — untouched (already decoupled).
- `config/config_loader.py` and `.env` — unchanged, still used by CLI only.
- `.env.example`, requirements.txt, LICENSE, README.fa.md — untouched.
- No Flask dependency added yet.

## How this enables the future Flask app
When you build the GUI later, a route just does:
```python
service = TaggerService(api_key=form_key, model="groq/compound-mini",
                        request_delay_seconds=form_delay, music_directory=form_dir)
result = service.process_all(on_progress=stream_to_client)
```
No `.env` read, no rewriting the pipeline. The service signature is the contract.

## Verification
- Run `python main.py` after the refactor → CLI output and behavior must be identical to before (same prints, same log file, same rename results).
- Confirm `core/service.py` has no `cli` or `config` imports (GUI-agnostic).
- Confirm `main.py` no longer contains the scan/rename/log loop inline.

## Risk
Low. The refactor moves existing, already-decoupled code into a service class. The only behavioral surface is the processing loop, which is preserved exactly and moved verbatim into `process_all`. The CLI callback ensures output stays identical.
